Overview

Managing requests for Workday security access

Workday Role Access, commonly called WRA, allows CALS employees to request security-role access to Workday for responsibilities involving areas such as human resources and business services.

A request can move through multiple review and approval stages. The application records its current state so that requestors and administrative teams can determine where the request is in the process and what action remains.

WRA also represents a newer CALS IT application architecture. Rather than building the entire user interface in Rails, the application separates responsibilities between a Vue.js frontend and a Rails REST API backend.

Workflow

Tracking a request from submission through completion

WRA maintains the state of each security-role request as it moves through the appropriate review and approval process.

01

Request

A CALS employee requests access to one or more Workday security roles.

02

CALS Review

The request is routed to the appropriate CALS HR and/or Business Services staff for review.

03

Approvals

The application tracks applicable division, supervisor, and campus approval states as the request progresses.

04

Workday

Once the required reviews are complete, the request can reach the stage where access is submitted in Workday.

Workflow Visibility

The application records where each request is in the process.

Requests can represent states such as approved, rejected, on hold, awaiting supervisor or campus action, or submitted in Workday. This gives the application a consistent way to represent a multi-step administrative process.

Application Security

Two different security questions

Authentication and authorization sound similar, but they solve two different problems. WRA needs both.

1

Authentication

Who are you?

Before WRA trusts a request, it needs to know who is using the application. UW–Madison's identity system performs that authentication rather than WRA collecting or validating the person's password itself.

Plain language: Think of this as showing your campus ID at the entrance. It establishes your identity.
2

Authorization

What are you allowed to do?

Knowing a person's identity does not automatically mean that person should be able to perform every action. WRA evaluates permissions separately using Manifest group membership and Rails authorization policies.

Plain language: Your campus ID gets you into the building. Authorization determines which rooms you are allowed to enter.

Authentication

OpenID Connect establishes the user's identity

WRA uses OpenID Connect, or OIDC, to authenticate users through UW–Madison's identity service.

Instead of asking a user to provide a password directly to WRA, the application sends the user to the university's trusted sign-in service. After authentication succeeds, the identity service returns information that WRA can validate and use to establish the current user.

In plain language

WRA asks UW–Madison, “Is this really Chris?”

UW–Madison handles the password and campus login. WRA receives cryptographically signed information confirming who authenticated.

This means the application does not need to create its own university-password system.

Secure Login Flow

Authorization Code Flow with PKCE

WRA uses the Authorization Code flow with PKCE to securely complete authentication between the Vue.js application and UW–Madison's identity provider.

1
User starts sign-in

The Vue.js application begins an authentication request.

↓
2
PKCE creates a one-time proof

The client creates a random secret for this login attempt and sends a transformed version of it with the request.

↓
3
UW–Madison authenticates the user

The user signs in through the university identity system.

↓
4
A temporary code is returned

The browser receives a short-lived authorization code rather than the user's credentials.

↓
5
The client proves it started the request

The original PKCE secret is supplied when exchanging the authorization code. The identity service verifies that it matches the proof created at the beginning.

↓
6
Tokens are returned and validated

The resulting identity and access information can then be used when communicating with the Rails API.

Why PKCE matters

Think of the authorization code as a claim ticket.

Receiving the ticket alone should not be enough to claim what it represents. PKCE creates a second piece of proof known only to the client that originally started the login.

If another application intercepts the authorization code, it does not also have the matching PKCE proof needed to successfully exchange that code.

API Authentication

The Rails API verifies the identity information it receives

The backend does not simply trust that a request contains something that looks like a valid token. The Rails API validates the signed token before using its identity information.

This includes verifying that the token was issued by the expected identity provider, is intended for the application, has not expired, and has a valid cryptographic signature.

In plain language

It is not enough to show an ID card. The API also verifies that the ID card is authentic.

Once the token passes those checks, its verified identity information can be used to establish the current user for that API request.

Authorization

Manifest groups and Pundit determine access

Once WRA knows who the user is, the next question is whether that person is permitted to perform the requested action.

1

Identity

Authenticated User

The Rails API has already verified who is making the request.

→
2

Membership

Manifest Groups

Group membership provides information about organizational or application-related access assigned to the person.

→
3

Policy

Pundit

Rails policy classes evaluate whether the current user is allowed to perform the requested action.

→
4

Decision

Allow or Deny

The API either continues with the request or returns an authorization error.

Manifest

Who belongs to which groups?

Manifest groups provide organizational membership information that WRA can use when determining whether a person has administrative or other application privileges.

Plain language: Think of Manifest as supplying the badges a person belongs to: for example, membership in an application administrator group.

Pundit

What does that membership allow?

Pundit keeps authorization rules in policy classes. Different resources can have policies describing who may view, create, modify, or perform other actions.

Plain language: Pundit acts like the security guard at each door. It checks the person's verified identity and permissions before allowing the action.

Putting It Together

The complete security story

01
OIDC

Establishes who the user is through UW–Madison's identity provider.

02
Authorization Code

Provides a temporary value used to complete the authentication exchange.

03
PKCE

Proves that the client redeeming the code is the same client that started the login.

04
JWT Validation

Allows the Rails API to verify the signed identity and access information it receives.

05
Manifest Groups

Provide group-membership information used when evaluating application access.

06
Pundit Policies

Decide whether the authenticated user may perform the requested action.

The Key Distinction

Login and permissions are intentionally separate.

OIDC, Authorization Code, PKCE, and token validation establish a trustworthy identity. Manifest groups and Pundit then use that identity to determine what the person is permitted to do.
