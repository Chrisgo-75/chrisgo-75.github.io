Overview

A data platform whose role has evolved over time

CALS Data was originally developed to give CALS applications a reliable local source for institutional people, employment, and organizational data. Campus data was synchronized into CALS-2, a MySQL database that applications could query without each application having to independently integrate with university data systems.

That architecture has changed as UW–Madison has created supported APIs for accessing institutional data. Newer CALS applications increasingly query campus APIs directly rather than depending on CALS-2 as their primary data source.

CALS Data still keeps CALS-2 current using sources such as the campus Person API and InfoAccess, but the database now serves increasingly as a reporting, auditing, and data-analysis resource rather than the primary integration layer for new applications.

Synchronization

Keeping CALS-2 aligned with campus data

CALS Data continues to synchronize information needed for CALS reporting and operational processes. Authoritative information is retrieved from campus systems and reconciled against existing CALS-2 records.

Synchronization includes people and employment information as well as Workday supervisory organization data. Maintaining organizational relationships locally makes it possible to answer CALS-specific reporting questions that require understanding where jobs fall within the university's organizational hierarchy.

An Important Distinction

CALS-2 is increasingly a reporting resource, not an application dependency.

As supported campus APIs have matured, newer applications can retrieve authoritative information directly. CALS-2 remains useful where synchronized data, organizational relationships, historical analysis, or complex reporting provide value.

Background Processing

Sidekiq handles scheduled and asynchronous work

Synchronization and auditing can involve large numbers of records and interactions with external systems. CALS Data uses Sidekiq to move this work outside the normal web request lifecycle.

Background jobs allow synchronization processes to run independently, while Sidekiq's web interface provides visibility into queues, active jobs, scheduled work, retries, and failures.

Data Integrity

Synchronization also needs verification

A successful API request does not necessarily prove that two systems remain synchronized correctly. CALS Data therefore includes reconciliation and auditing processes that compare authoritative campus information with CALS-2.

These checks help identify missing records, unexpected employment differences, stale information, or other conditions that require investigation.

Treating verification as part of the synchronization process makes the data pipeline more observable and provides another way to detect changes in upstream systems before they become reporting problems.

Evolution

Adapting as campus data access changes

One of the defining characteristics of CALS Data is that its purpose and integrations have changed while the system has remained useful.

01

Local Application Data

CALS-2 initially provided a common local database that CALS applications could query for institutional people and employment data.

02

Campus APIs Mature

UW–Madison began providing supported APIs that gave applications direct access to authoritative institutional information.

03

Integration Strategy Changes

New CALS applications increasingly consume campus APIs directly rather than depending on CALS-2.

Reporting & Analysis

CALS Data continues maintaining CALS-2 where synchronized data provides value for reporting, auditing, organizational queries, and operational analysis.

Engineering Challenges

More than moving data from one system to another

Reliable Synchronization

Keeping local data aligned with authoritative systems while correctly handling new, changed, inactive, and terminated records.

Changing Source Systems

Adapting long-running integration logic as campus systems move from warehouse-oriented access toward supported institutional APIs.

Organizational Hierarchies

Maintaining Supervisory Organization relationships that make queries such as ARS HQ employment reporting possible.

Data Reconciliation

Determining whether differences represent synchronization problems, source-system changes, or legitimate business conditions.

Outcome

A long-running integration system that continues to provide value as its role changes.

CALS Data has evolved from primarily supporting application data access into a platform for synchronized reporting, auditing, and operational analysis. At the same time, newer CALS applications are able to take advantage of supported campus APIs and retrieve authoritative data directly.

Maintaining CALS Data through that transition has required adapting integrations and data models while preserving the reporting capabilities that continue to support CALS business processes.
